===========================================================
BlackPoker 対戦進行上のショートカット指針
===========================================================

目的
====

BlackPokerは、相手の行動に対して割り込めるターン制ゲームです。
通常アクションのリクエストがステージにある間は、
チャンスを持つプレイヤーに割り込みの機会が与えられます。
即時アクション自体への割り込みはできません。

しかし、実際の対戦で毎回「何かありますか？」「パスします」とやり取りしていては、
ゲームのテンポが損なわれます。
そこで、多くの対戦では **暗黙の了解** によって一部のチャンスが自然に省略され、
スムーズに進行しています。

本指針は、こうしたプレイヤー間で自然に育まれてきたプレイ文化を
「ショートカット」として言語化し、テンポよく、かつ公平に対戦を進めるための
共通認識を示すものです。


本文ルールとの関係
==================

本指針は、BlackPokerを円滑に進行するための推奨運用を示すものです。
本指針の記述が、総合ルール(コアフロー等)の記述と矛盾する場合は、総合ルールの記述を優先して適用します。


用語の定義
==========

本指針では、解説を明確にするため、次の呼称を使用します。

* **ターンプレイヤー(TP)**: 現在自身のターンを進行しているプレイヤー。
* **非ターンプレイヤー(NTP)**: 現在ターンを行っていない側の(相手のターン中の)プレイヤー。


ショートカットの原則
====================

ショートカットは、次の原則に基づいて成立します。
個別に列挙されていない場面であっても、この原則に従って省略が行われます。

原則1：反応がなければパスとみなす
---------------------------------

通常アクションを宣言したプレイヤーがパスして相手にチャンスを渡し、相手が特に反応を示さなければ、
相手はその時点のチャンスを **パスした** ものとみなします。
宣言したプレイヤーのパスも、両者の認識が一致している範囲で省略できます。
ただし、パスできるのはステージにリクエストが存在する場合に限ります。
ステージが空の場面での沈黙をパスとして扱うことはできません。

これはコアフローにおける「チャンス」と「パス」の仕組みに基づいています。
コアフローでは、全員がパスするとステージ上の最後のリクエストを1件解決します。
その後にリクエストが残っている場合も、次の1件を解決する前に改めて応答する機会があります。
実際の対戦では、この「全員のパス」が暗黙に行われることで、
宣言されたアクションが自然に解決へと進みます。


原則2：連続する手順をまとめて進行できる
----------------------------------------

プレイヤーは、互いに関連する一連の手順を **まとめて進行することを暗黙に提案** できます。
相手がその進行を止めなければ、提案された手順がすべて完了したものとして扱います。

たとえば、あるアクションの解決後に誘発するアクションが明らかな場合、
いちいち確認せずにまとめて処理を進めることができます。


原則3：割り込みの権利は常に保障される
--------------------------------------

ショートカットによって省略されるのは
**「特に何もしない」という確認のやり取り** であり、
**割り込みの権利そのものが失われるわけではありません。**

相手がショートカットで先に進もうとしたとしても、
プレイヤーはいつでも「対応して」「待ってください」などと宣言して
進行を止めることができます。

.. note::

   割り込みの宣言に特別なコール(掛け声)は強要しませんが、
   相手に **「進行を止めたい」** という意思が明確に伝わる言葉を用いることを推奨します。

原則4：認識のずれは巻き戻す
----------------------------

ショートカットによる省略が原因で、
両者の認識にずれが生じた場合は、
**直前の明確な地点まで巻き戻して** 確認・処理を行ってください。


運用上の注意
============

* ショートカットは、 **両者の認識が一致している範囲でのみ有効** です。不明な点があれば、遠慮なく確認してください。

* リクエストの宣言と同時にいきなりカードを出す・ドライブするなど、 **相手の応答機会を奪う進行は避けてください。**

* 割り込みたいプレイヤーも、相手が次の処理に進む前に明確な宣言を行うよう心がけてください。

* 本指針は全てのショートカットを網羅するものではありません。ここに記載されていない場面でも、原則に基づきプレイヤー間の合意で省略は成立します。


標準ショートカット
==================

原則に基づいて自然に成立するショートカットのうち、
特に頻出するものを次に示します。

これらはあくまで **代表的な例** です。
原則に基づけば、ここに記載されていない場面でも省略は成立します。


メインアクションの実行
----------------------

多くのメインアクション(兵士召喚、装備など)は、
TPが宣言し、NTPが黙認することで解決に進みます。

.. code-block:: text

   TP: 「兵士召喚します」
   NTP: (特に反応なし)
   → リクエストが解決される

NTPが割り込みたい場合は、解決前に宣言します。

.. code-block:: text

   TP: 「兵士召喚します」
   NTP: 「対応して、ダウンを使います」

* **ルール上の効果**:
  この会話例では、TPが宣言後にパスしてNTPへチャンスを渡す確認を、両者の合意で省略しています。NTPも反応しなければパスしたものとみなし、全員パスの成立によってリクエストを解決します。対応する例でも、NTPはTPのパス後に応答しています(原則1)。


アタックの進行
--------------

アタックからダメージ判定までは、誘発によって「アタック → ブロック → ダメージ判定」と連続して進行します。
この区間にはチャンスが複数回発生しますが、実際の対戦では多くが暗黙にパスされます。

次に、段階ごとの流れと省略のされ方を示します。

**1. アタックの宣言**

.. code-block:: text

   TP: 「アタックします」
   NTP: 「どうぞ」

* **ルール上の効果**:
  この会話例では、TPのパスを両者の合意で省略し、NTPへチャンスを渡しています。NTPの「どうぞ」は、アタック **リクエスト** に対してパスする意思表示です(原則1)。NTPはクイックアクション(ツイストやダウンなど)で対応することもできます。両者がパスするとアタックが解決され、TPがアタッカーを指定します。

NTPがアタック解決前に割り込みたい場合：

.. code-block:: text

   TP: 「アタックします」
   NTP: 「対応して、〇〇を使います」

**2. ブロッカーの指定**

アタックが解決されアタッカーが指定されると、ブロックアクションが誘発します。

.. code-block:: text

   NTP: 「♠10を♦2でブロック」

* **ルール上の効果**:
  ブロックがステージに積まれ、誘発チェックを終えると、まずTPにチャンスとフォーカスを設定します。TPがパスするとNTPへチャンスが移り、NTPもパスするとブロックが解決され、NTPがブロッカーを指定します。この例では、両者の合意でパスの確認を省略しています。どちらも、自分がチャンスを持つ時点で、パスせず合法なクイックアクションをリクエストできます(原則1・3)。

**3. ダメージ判定**

ブロックが解決されると、ダメージ判定アクションが誘発します。

.. code-block:: text

   TP: 「ダメージ判定に入ります」
   NTP: (特に反応なし)
   → ダメージ判定が解決される

* **ルール上の効果**:
  ダメージ判定が解決される前に、TP・NTPの双方にチャンスがあります。TPが「何もありません」「パス」と言ったり、あるいは暗黙にパスした後、NTPにもチャンスが移ります。NTPも何もなければ、ダメージ判定が解決されます。どちらかが割り込みたい場合は「対応して」と宣言します(原則3)。

**ブロックしない場合の省略**

NTPがブロッカーを指定せず、ダメージ判定まで一括して進行を認める場合もあります。

.. code-block:: text

   TP: 「アタックします」
   NTP: 「受けます」
   TP: 「では、✕ダメージで」

* **ルール上の効果**:
  NTPの「受けます」は、アタック解決の了承に加えて、 **ブロッカーを指定せず、ダメージ判定まで進行を認める** という意思表示として扱います。アタック解決後のチャンス、ブロッカー指定、ダメージ判定前のチャンスを一括でパスしたものとみなされます(原則2)。


ターンの受け渡し(エンド→チャージ→ドロー)
--------------------------------------------

ターンの受け渡しでは、エンドの解決後、誘発によってチャージ・ドローと進行します。

エンドが全員パスを経て解決されると、旧NTPが新TPになります。
誘発チェックでチャージを即時解決し、ドローをステージに積みます。
誘発チェックを終えたら、まず新TPにチャンスとフォーカスを設定します。
新TPがパスすると、新NTP(旧TP)へチャンスが移ります。フォーカスは新TPのままです。
新NTPもパスすると、全員パスが成立してドローを解決します。

両者の合意があれば、新TPのパスの確認を省略して新NTPの応答確認へ進めます。
新TPのチャンスがなくなるわけではなく、新TPはパスする前に合法なクイックアクションをリクエストできます。

**何もない場合**

.. code-block:: text

   TP: 「エンド」
   → 両者のパス → エンド解決(ターン切り替わり)
   → チャージ(即時解決) → ドローをステージに追加
   新TP(旧NTP): 「ドロー、何もなければ引きます」
   新NTP(旧TP): (特に反応なし)
   → 全員パス成立 → ドロー解決

* **ルール上の効果**:
  エンド解決前の両者のパスは、合意に基づいて確認を省略できます。ドローに対する新TPの発言は、自分のパスと相手への応答確認をまとめた提案です。新NTPが反応しなければパスしたものとみなし、全員パスの成立によってドローを解決します。ドローを積んだだけで新NTPへチャンスが移るわけではありません(原則1・2)。

**エンドに対応する場合**

NTPがエンドに対してアクションを行いたい場合は、エンド解決前に宣言します。

.. code-block:: text

   TP: 「エンド」
   NTP: 「エンドの前に(または、エンドに対応して)、〇〇します」

* **ルール上の効果**:
  この例では、TPのパスの確認を両者の合意で省略し、チャンスを得たNTPがエンド解決前に割り込みを宣言しています(原則1・3)。エンドはステージに積まれた状態で一時停止し、NTPのアクションから先に処理します。

**ドローに対応する場合**

新NTP(旧TP)は、新TPのパスが明示されるか、合意に基づいてその確認を省略した後に、ドローへ応答できます。

.. code-block:: text

   TP: 「エンド」
   → 両者のパス → エンド解決(ターン切り替わり)
   → チャージ(即時解決) → ドローをステージに追加
   新TP(旧NTP): 「パス。ドローに対応はありますか？」
   新NTP(旧TP): 「ドローに対応して、〇〇します」

* **ルール上の効果**:
  誘発チェック終了後にまず新TPがチャンスを持ち、そのパスによって新NTPへチャンスが移ります。この例では新TPのパスを明示していますが、合意があればその確認を省略できます。新NTPは得たチャンスで合法なクイックアクションをリクエストします。対応しない場合はパスし、全員パスの成立によってドローを解決します(原則1・3)。
